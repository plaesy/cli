# Hermes API server — documented acceptance scenarios

**Purpose:** Convert the pinned Hermes API-server documentation into falsifiable candidate scenarios for later incumbent reproduction and Plaesy parity work. This is not an implementation spec, test result, or replacement claim.

**Source baseline:** Hermes Agent commit `40d1e95f37e409f9f618f32c170661c66b86a4f4`; [API Server feature page](https://github.com/NousResearch/hermes-agent/blob/40d1e95f37e409f9f618f32c170661c66b86a4f4/website/docs/user-guide/features/api-server.md). Reviewed 2026-11-17. Auth/run-admission and Runs SSE code were additionally inspected at this commit: [`api_server.py`](https://github.com/NousResearch/hermes-agent/blob/40d1e95f37e409f9f618f32c170661c66b86a4f4/gateway/platforms/api_server.py), [`api_server_runs.py`](https://github.com/NousResearch/hermes-agent/blob/40d1e95f37e409f9f618f32c170661c66b86a4f4/gateway/platforms/api_server_runs.py), [`api_server_run_idempotency.py`](https://github.com/NousResearch/hermes-agent/blob/40d1e95f37e409f9f618f32c170661c66b86a4f4/gateway/platforms/api_server_run_idempotency.py), and [`test_api_server_runs.py`](https://github.com/NousResearch/hermes-agent/blob/40d1e95f37e409f9f618f32c170661c66b86a4f4/tests/gateway/test_api_server_runs.py). The endpoint-map additions are coverage candidates; rows marked `CODE REVIEW` are implementation-derived and are not promised by the public documentation. Refine them against focused tests before treating them as normative compatibility requirements. This audit did not establish targeted queue-overflow, replay-gap, or post-expiry reconnect tests.

1. Re-read the entire pinned source sections and relevant route/store/auth code; refine scope, modes, retention, identity fields, and failure cases per scenario.
2. Reproduce the scenarios against the pinned Hermes checkout using a disposable profile and non-sensitive fixtures. Capture command, commit, environment, and output/state. For `AC-F-HERMES-API-005-02`, verify the run idempotency store is file-backed and available before expecting restart replay; separately exercise the documented in-memory fallback without claiming persistence.
3. Map each scenario to Plaesy routes, authorization policy, persistence model, and focused tests. Preserve the documented distinction between liveness and readiness, authenticated profile routing, canonical and legacy idempotency, and run terminal states.
4. Add security/fault cases for unauthenticated and cross-profile access, duplicate admission, conflict, timeout, cancellation, restart, storage unavailable, session deletion/tombstones, and response/run retention where in approved scope.
5. Mark `VERIFIED_INCUMBENT` or `PLAESY_VERIFIED` only after evidence meets `feature-measurement-framework.md`; this document alone cannot change feature status.
